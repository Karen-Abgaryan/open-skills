# HH Market Analysis

Announce at start: "I'm using the hh-market-analysis skill to analyse the hh.ru labour market data."

Анализ рынка труда по выдаче и фасетам hh.ru. **Только чтение.** Аккаунт работодателя
с активным биллингом (действие стоит 300 ₽), поэтому запрет платных действий встроен в
`assets/hh-lib.js` конструктивно, а не декларативно.

## Три факта, которые определяют весь подход

1. **Зарплаты видны без покупки доступа к базе.** Право
   `VIEW_DESIRABLE_COMPENSATION` при `permission: view_without_contacts`. Закрыты
   только контакты.
2. **Текстовый поиск работает, но только в присутствии `exp_period`.** Одного `text`
   мало: без спутника `exp_period` запрос принимается, попадает в `criteria` и **молча
   не фильтрует** — числа получатся, и они будут описывать весь пул. Рабочая связка —
   `text` + `pos` + `logic` + `exp_period`; интерфейс hh всегда шлёт `exp_period`, а
   собранный вручную URL — нет, отсюда и ловушка. `buildUrl` требует все четыре.
   Область поиска задаётся `pos`, в том числе `pos=education` — вуз, факультет,
   специальность.
3. **Смысловые признаки размечаются после сбора.** Грейда, отрасли, уровня владения
   навыком в фильтрах нет, но `title` и должности из `shortExperience` лежат в выдаче.
   Схема: широкий структурный запрос → классификация выгрузки у себя.

## Требования

Playwright MCP (`mcp__playwright__*`), аккаунт **работодателя**, ручной вход
пользователя. Соискательский аккаунт `/search/resume` не видит.

## Рабочий цикл

1. **Уточнить предмет с оператором.** Профроль, регион, опыт, требования. Границы
   запроса — это предмет исследования, а не пожелание; расширять их самовольно нельзя
   (`references/protocol.md`).
2. **Открыть hh.ru и проверить вход.** `browser_navigate` на
   `https://hh.ru/search/resume`, затем `checkAuth()`. Если не авторизован —
   **остановиться и попросить оператора войти**, не пытаться логиниться самому.
3. **Загрузить библиотеку** (см. ниже). Переинъекция нужна после каждой навигации.
4. **Разрешить названия в id.** `resolveIds('professional_role', 'аналитик')`,
   `resolveIds('skill', 'DWH')`. Подсказки ищут по префиксу и пропускают синонимы —
   для семейства навыков использовать seed + фасет `skill` (`references/strategy.md`).
5. **Обзор одним запросом.** `overview(spec)` → `totalResults` + все фасеты + L0. Часто
   этого уже достаточно для ответа.
6. **Верифицировать** — L0 всегда, L1 для непроверенных параметров
   (`references/verification.md`).
7. **Собрать выгрузку**, если нужны медианы или разрезы. `harvest(spec, maxPages)`;
   при объединении синонимов — по одному прогону на тег. Факультет, специальность и
   год выпуска живут только в карточке: `harvestCards(hashes)`, предварительно
   объявив оператору цену в карточках и календарных днях (`references/protocol.md`).
8. **Посчитать и проверить.** Сохранить каждый прогон в JSON, затем `analyze.py` —
   L2, когорты, перцентили, классификация, таблица точечной проверки. Модуль правил
   классификации сохранять рядом с выгрузкой в рабочем каталоге, а не во временном:
   разметка домена и грейда воспроизводится только вместе с ним, и повторный прогон
   без него даст другие когорты при тех же данных.
9. **Отчёт** по обязательному списку из `references/verification.md`.

## Загрузка библиотеки

Прочитать `assets/hh-lib.js` и вставить его целиком телом стрелочной функции в
`browser_evaluate`, добавив в конец `return window.__hh.VERSION;`. Файл — самодостаточный
IIFE, объявляющий `window.__hh`. Дальнейшие вызовы становятся однострочными:

```js
async () => await window.__hh.overview({
  professional_role: [148], area: 1,
  relocation: 'living', search_period: 365,     // оба обязательны
  experience: ['moreThan6'], skill: [1114],
})
```

Сохранять выгрузку в файл для `analyze.py`: вернуть `JSON.stringify(result)` из
`browser_evaluate` **с параметром `filename`**. Выгрузка в пару тысяч резюме весит
мегабайты и через текстовый ответ инструмента не проходит — Write-инструментом её не
переложить. Файл падает в рабочий каталог, а не в каталог Playwright. Результат при
этом кодируется повторно; `analyze.py` разворачивает такую обёртку сам.

## API `window.__hh`

| Функция | Назначение |
|---|---|
| `checkAuth()` | `employerId`, `canSearchResumes` |
| `resolveIds(kind, text)` | Названия → id (`skill`, `area`, `university`, `professional_role`) |
| `buildUrl(spec, path?)` | Спека → URL; требует `relocation`, `search_period`, а при `text` — ещё `pos`, `logic`, `exp_period` |
| `assertSafe(url)` | Белый список путей, только GET, платные паттерны в пути и в именах параметров |
| `overview(spec)` | 1 запрос → `totalResults` + все фасеты + `droppedParams` |
| `filterEfficacy(spec, params)` | **L1**: снимает параметры по одному, сверяет `totalResults` |
| `harvest(spec, maxPages, opts)` | Сбор со случайными паузами, дедуп, потолок, стоп при 429/403 |
| `harvestCards(hashes, opts)` | Вскрытие карточек ради образования: счётчик суточной квоты, стоп при 409, возобновляемая очередь |
| `randomPages(total, n)` | Случайные страницы — `order_by=relevance` смещён |
| `sliceBySalary(spec)` | Рекурсивная нарезка при `totalResults > 5000` |
| `spotCheck(rows, n)` | Случайные ссылки на карточки с разобранными значениями |
| `vacancyOverview(spec)` | Сторона спроса, с полями `gross` и `mode` |
| `facets(state)`, `parseRow(raw)`, `criteriaDiff(url, criteria)` | Разбор состояния |

## Скрипт статистики

```
python3 ~/.claude/skills/hh-market-analysis/scripts/analyze.py dwh.json etl.json \
    --classify grade --spot-check 10 --seed 42
```

Несколько файлов **сливаются и дедуплицируются по hash** — так собирается объединение
синонимов по ИЛИ, которого сервер не умеет. Выдаёт markdown: L2-целостность, когорты,
перцентили, грейды, таблицу точечной проверки. Только стандартная библиотека.

Разрезы сверх грейда задаются своим модулем правил, а не переписыванием скрипта:

```
analyze.py msu.json --rules rules_msu.py --dimension faculty --cards cards.json
```

Модуль объявляет `DIMENSIONS = {'<измерение>': [(регулярное выражение, метка), …]}`;
правила проверяются сверху вниз, поэтому частные идут перед общими. Отсутствие
значения получает собственную метку и никогда не сливается с «прочим». Таблица
точечной проверки печатает, какое правило сработало на каждой строке, — так виден
перехват общим правилом того, что должно было достаться частному.

## Верификация — три уровня плюс ручная сверка

Подробности и критерии провала: `references/verification.md`.

| Уровень | Что ловит | Цена | Инструмент |
|---|---|---|---|
| **L0** Preflight | Ушёл не тот запрос: не авторизован, запрещённый или отброшенный параметр | 0 | `checkAuth`, `assertSafe`, `buildUrl`, `criteriaDiff` |
| **L1** Эффективность фильтра | Параметр принят, но не фильтрует — как `text` | +1 запрос на параметр | `filterEfficacy` |
| **L2** Целостность выборки | Сбор неполон, упёрся в потолок 5000, смещён, потерял записи | 0 | `analyze.py` |
| **Ручная** сверка | Разбор не соответствует тому, что показано на странице | Время оператора | `analyze.py --spot-check` |

L0 и L2 бесплатны и выполняются **всегда**. L1 обязателен для `verified_skills`,
одиночного `education` и любого параметра, впервые используемого в задаче. Таблица
точечной проверки включается в отчёт как доказательство, что сверка проводилась.

## Жёсткие правила

- `text` без `exp_period` **молча не фильтрует** — не «падает», а возвращает весь пул с
  текстом в эхе `criteria`; слать всегда четвёркой `text` + `pos` + `logic` +
  `exp_period` и подтверждать L1, что `totalResults` изменился;
- значение `exp_period` на текстовый отбор не влияет (`all_time` и `last_year` дают
  одинаковый результат) — это условие применения текста, а не его модификатор;
- смысловые признаки (грейд, отрасль, «сложный SQL») не искать фильтром, а размечать
  после сбора;
- id профроли — не гарантия профессии: крупная роль (например, руководящая) собирает
  заметную долю чужого домена — стройки, производства, логистики, эксплуатации.
  Разметить домен на базовой выборке и посмотреть долю чужого **до** расчёта зарплат —
  иначе медиана опишет смесь двух рынков, не подав никакого признака этого;
- требование раскрывать в **семейство синонимов и объединять по ИЛИ** (запрос на тег +
  склейка по `hash`), а не пересекать: объединение даёт сотни значений с зарплатой
  там, где пересечение даёт единицы;
- синонимы искать через seed-навык и фасет `skill`, а не через `suggests`;
- не более двух узких навыков в одном пересечении; остальные требования измерять
  фасетом `skill`, а не отсеивать;
- карточка `/resume/<hash>` денег не стоит, но расходует квоту **500 просмотров
  резюме в сутки** на аккаунт со сбросом в 00:00 МСК; исчерпав её, hh отдаёт
  `errorCode 409` вместо данных — это лимит, а не сбой сети, ретраи и удлинение пауз
  бесполезны, и расширение образовательных разрезов стоит календарных дней. Поиск и
  фасеты под квоту не попадают;
- три зарплатные когорты (заявлено / только оценка hh / ничего) **не смешивать** —
  оценка составляет около 0.68 заявленного; средняя когорта при этом почти всегда
  пуста (на больших сборах — ни одной), это свойство данных, а не потеря при разборе;
- пороги публикации: n с зарплатой ≥ 50 — перцентили, 10–49 — перцентили с
  оговоркой «ориентировочные», < 10 — только сырые значения без медианы; порог — не
  приговор: узкую группу, заданную тегом `skill`, добирают текстовым поиском по
  `pos=workplace_organization` и `pos=workplace_description` со склейкой по `hash` —
  так целевая выборка поднимается с единиц до десятков значений с зарплатой и
  переводит оценку через порог;
- измерение, доступное лишь по вскрытым карточкам, публиковать в двух долях сразу —
  от всей выборки и от вскрытой части, со строкой «карточка не вскрыта» в таблице;
- форматы работы не считать разбиением — сегменты пересекаются, сумма превышает базу;
- `employment` и `schedule` — легаси-алиасы: сервер молча переводит их в
  `employment_form` и `work_format`, теряя значения без пары: `employment=part` и
  `employment=project` схлопываются в один `PART_TIME` (состав выдачи полностью
  совпадает), `schedule=shift` и `schedule=flexible` не фильтруют вовсе — замены на
  стороне резюме нет. Задавать `employment_form` и `work_format` напрямую; словари у
  резюме и вакансий разные — на резюме `PART_TIME`, на вакансиях `PART`, а
  `PART_TIME` там молча игнорируется;
- счётчик фасета считается по недедуплицированному пулу и сходится с
  `totalUngroupedResults`, а не с `totalResults` фильтрованного запроса — превышение
  на 11–17% нормально и не означает сломанного фильтра; объёмы сегментов считать
  прямым запросом;
- `relocation` задавать явно; умолчание завышает регион на ~26%;
- `search_period` задавать явно; умолчание 30 дней;
- `education_level` перечислять полностью, «и выше» не существует;
- несколько `skill` — это И, не ИЛИ;
- `items_on_page=100`, `page ≤ 49`, потолок `max_search_result=5000`;
- бакеты зарплатного фасета **адаптивные** — между разными запросами несопоставимы;
  для сравнения рынков задавать одинаковые `salary_from`/`salary_to` или считать
  перцентили по выборке;
- нарезка по `salary_from`/`salary_to` отбирает только резюме с **указанной**
  зарплатой — объединение срезов равно зарплатной когорте, а не популяции;
- эхо `criteria` ≠ работающий фильтр; настоящая проверка — изменение `totalResults`;
- у `<template>` читать `el.innerHTML`, **не** `textContent` (тот вернёт пустую строку);
- паузы случайные, потолок 20 страниц на прогон, остановка без ретраев при 429/403;
- только GET из белого списка; никаких кликов, никаких мутаций, `xsrfToken` не трогать;
- в отчёт — только агрегаты; персональные данные не выгружать и не сохранять.

## Справочные файлы — читать по триггеру, а не подряд

Всё выше самодостаточно для типовой задачи: обзор рынка, зарплатные перцентили, топ
навыков, сравнение со спросом. Справочники **не входят в обязательное чтение** — они
открываются, когда здесь чего-то не хватает или что-то пошло не так. Если задача
укладывается в рабочий цикл и ничего не ломается, не открывать ничего.

| Триггер | Файл |
|---|---|
| Нужно точное значение параметра, enum, id, имя фасета или поле записи, которого нет выше | `references/filters.md` |
| Фильтр повёл себя неожиданно; `totalResults` не сходится; упёрлись в потолок 5000 | `references/filters.md` |
| Понадобилась сторона спроса или выяснилось, что раздел hh недоступен | `references/filters.md` |
| Зарплатные числа выглядят странно; нужны пороги очистки, шкала `predictedSalary`, нормализация gross/net | `references/salary.md` |
| Выборка обвалилась; требование сложнее одного тега; нужны грейды, отрасли или образование | `references/strategy.md` |
| Проверка L0/L1/L2 дала провал; пора публиковать отчёт | `references/verification.md` |
| Нужно отклониться от буквального запроса; пришли 429/403/капча; понадобилось вскрывать карточки; карточки отдают `errorCode 409` | `references/protocol.md` |
| Нужен enum или id без обращения к сети | `references/dictionaries.json` |

**Исключение — «Жёсткие правила» выше.** Они перечисляют ловушки, которые не дают о
себе знать: запрос отработает, числа получатся, и они будут неверны. Никакой
«сложности», по которой можно было бы догадаться открыть справочник, не возникнет —
поэтому эти правила лежат здесь, а не в файлах.
