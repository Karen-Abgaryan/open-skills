# Верификация результата

Три уровня плюс ручная точечная проверка. Каждый ловит свой класс ошибок, и ни один не
заменяет другой. L0 и L2 бесплатны и выполняются **всегда**; L1 стоит по запросу на
проверяемый параметр; точечная проверка стоит времени оператора.

| Уровень | Что ловит | Цена | Когда |
|---|---|---|---|
| L0 Preflight | Запрос ушёл не тот, что задумывался | 0 | Всегда, до сбора |
| L1 Эффективность фильтра | Параметр принят, но не фильтрует | +1 запрос на параметр | При любом непроверенном параметре |
| L2 Целостность выборки | Собрано не то или не всё | 0 | Всегда, после сбора |
| Точечная проверка | Разбор не соответствует странице | Время оператора | Перед публикацией отчёта |

## L0 — Preflight

Выполняется **до** сбора. Ничего не стоит, ловит самые дорогие ошибки — те, из-за
которых собирается не та популяция.

### 1. Аутентификация

```js
window.__hh.checkAuth()   // {authed, employerId, canSearchResumes}
```

`authed: false` или `canSearchResumes: false` → **остановиться и попросить оператора
войти**. Не полагаться на память о прошлой сессии: профиль браузера персистентный,
но сессия истекает. Проверять каждый прогон.

### 2. Безопасность URL

`assertSafe(url)` вызывается внутри каждого запроса библиотеки и бросает исключение
на всём, что вне белого списка GET. Это конструктивный запрет, а не декларация:
обойти его можно только написав собственный `fetch` в обход библиотеки — чего делать
нельзя.

### 3. Запрещённые и обязательные параметры

`buildUrl` отклоняет `prompt_text` (AI-поиск на аккаунте выключен) и требует явных
`relocation` и `search_period`. Умолчания hh (`living_or_relocation`, 30 дней) меняют
ответ молча: первое завышает регион на ~26%. При заданном `text` требуются ещё `pos`,
`logic` и `exp_period`: без `exp_period` текст принимается и не фильтрует, без `pos` и
`logic` — не разбирается вовсе.

### 4. Сверка эха criteria

Бэкенд возвращает свой разбор запроса в `criteria`. `criteriaDiff` показывает
параметры, которые ушли, но в разборе отсутствуют — их бэкенд отбросил.

```js
const o = await window.__hh.overview(spec);
o.droppedParams   // [] — хорошо; непусто — параметр не понят
```

`overview` и `harvest` считают это сами; `analyze.py` выносит непустой результат в
отчёт как **выделенное предупреждение**.

**Эхо не доказывает, что фильтр работает** — `text` без `exp_period` проходит эхо и не
фильтрует. Для этого нужен L1.

## L1 — Эффективность фильтра

Проверяет ровно то, чего не проверяет L0: что параметр не просто понят, а действительно
сузил выборку.

```js
await window.__hh.filterEfficacy(spec, ['skill', 'experience', 'verified_skills']);
```

Снимает по одному параметру и пересчитывает `totalResults`. Логика:

| Наблюдение | Вывод |
|---|---|
| Без параметра результатов **больше** | Фильтр работает |
| Без параметра результатов **столько же** | Параметр игнорируется |
| Без параметра результатов **меньше** | Аномалия, разбираться до публикации |

Стоимость — один запрос на проверяемый параметр, плюс случайные паузы. Прогонять
обязательно для:

- `text` — он применяется только вместе с `exp_period`, а без него принимается,
  отражается в эхе и не фильтрует; L1 — единственное, что отличает эти два случая;
- `verified_skills` — комбинирование не тестировалось;
- одиночного `education` — семантика не выяснена;
- любого параметра, впервые используемого в этой задаче;
- всего набора, если результат выглядит подозрительно круглым или подозрительно
  совпадающим с базой.

Побочная польза: `withoutTotal` против `baseTotal` показывает **вклад каждого
фильтра** в сужение — то есть сразу видно, какой фильтр обвалил выборку, и это готовый
материал для разговора с оператором о послаблениях.

## L2 — Целостность выборки

Считается по уже собранным данным, дополнительных запросов не требует. Делает
`analyze.py` — раздел «L2 — целостность выборки».

| Проверка | Что означает провал |
|---|---|
| `pagesFetched` против `pagesRequested` | Сбор прервался; причина в `stoppedReason` |
| `stoppedReason` непусто | 429 / 403 / капча / пустая страница — **сбор неполон** |
| `capHit` | `totalResults` > `max_search_result`: хвост недостижим, перцентили описывают только доступную часть. Нужна нарезка по зарплате |
| Покрытие популяции | `pagesFetched × 100 / totalResults`. Низкое покрытие + `order_by=relevance` = смещённая выборка |
| `duplicates` внутри файла | Норма при склейке страниц; аномально высокое значение — признак сбоя пагинации |
| Пересечение источников | При объединении синонимов показывает, насколько теги дублируют друг друга |
| `droppedParams` (из L0) | Повторно выносится сюда, чтобы не потерялось |
| Записи без `hash` | Не дедуплицируются — искажают все счётчики |
| Уровни `permission` | Всё, кроме `view_without_contacts`, требует объяснения |
| Отброшено вне диапазона / в иной валюте | Печатается числом, а не прячется |
| `n` по каждой когорте | Основание для порога перцентилей |

Всё, что отброшено при очистке, попадает в отчёт числом. Молча отброшенных значений
быть не должно.

## Точечная проверка оператором

L0–L2 проверяют, что собрано **то, что просили**, и что оно **целое**. Они не
проверяют, что разбор JSON соответствует тому, что реально показано на странице.
Единственный способ это подтвердить — открыть несколько карточек глазами.

`analyze.py --spot-check N` печатает таблицу: случайные N записей, ссылка
`https://hh.ru/resume/<hash>` и рядом значения, которые из этой записи разобрал сбор.

```
python3 ~/.claude/skills/hh-market-analysis/scripts/analyze.py rows.json --spot-check 10 --seed 42
```

Оператор открывает несколько ссылок и сверяет: заявленная зарплата, желаемая
должность, регион, стаж, статус поиска.

- **Выборка случайная**, а не первые N — `order_by=relevance` смещён, а первые записи
  выглядят «слишком хорошо».
- `--seed` фиксирует состав выборки, чтобы проверку можно было повторить.
- Открытие карточки — обычный `GET` при `view_without_contacts`, **ничего не
  расходует**. Контакты остаются закрытыми.
- Расхождение значит **ошибку разбора**, а не шум данных — публиковать отчёт до
  выяснения нельзя.
- 10 записей достаточно, чтобы поймать систематическую ошибку разбора (перепутанные
  `salary` и `predictedSalary`, потерянная двойная вложенность `jobSearchStatus`,
  необёрнутый массив). Единичные расхождения ищутся не так.

Таблица точечной проверки включается в отчёт — она же служит доказательством, что
проверка проводилась.

## Границы доверия: что не проверено

Указывать в отчёте, когда результат от этого зависит:

- Реальные пороги rate limiting и поведение капчи. Намеренно не прощупывались.
- Причина неработающего `text` — гипотеза о платной услуге не подтверждена.
- Появится ли образование в выдаче, если включить его через «Вид» в интерфейсе.
- Заполненность `year` проверена на небольшой выборке одного вуза.
- Включительность границ `salary_from`/`salary_to` при нарезке — двойной учёт на
  стыках вероятен.
- Точная семантика одиночного параметра `education`.
- Комбинирование `verified_skills` — И или ИЛИ, не тестировалось.
- Изменится ли поведение `text` после покупки доступа к базе.
- Алгоритм `predictedSalary` и смысл `liveness.score` — недокументированы.
- `professionExperience.professionId` — справочник не найден.

## Обязательное в отчёте

Дата; регион и **значение `relocation`**; полный набор фильтров и итоговый URL;
`search_period`; `totalResults` против размера выборки; по каждой зарплатной когорте —
`n` и доля; число отброшенных выбросов и иных валют; состав семейства синонимов
целиком; оговорка gross/net при сравнении с вакансиями; таблица точечной проверки.

Если вскрывались карточки — сколько вскрыто из выборки, и по каждому карточному
измерению **обе доли**: от всей выборки и от вскрытой части. Доля от вскрытых, поданная
как доля пула, завышает признак во столько раз, во сколько вскрытая часть меньше
выборки.

Без `relocation` и без разбивки по когортам числа невоспроизводимы и, скорее всего,
неверны.

В отчёт идут **только агрегаты**. Персональные данные не выгружать и не сохранять;
ссылки в таблице точечной проверки — рабочий инструмент проверки, а не выгрузка базы.
