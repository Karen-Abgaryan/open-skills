## Где обваливается выборка

Навыки комбинируются через И, и каждый добавленный режет выборку в разы. Пример одного
замера (системный аналитик, Москва, `relocation=living`, опыт 6+, `search_period=365`):

| Фильтр | Всего | С зарплатой | Доля |
|---|---|---|---|
| без навыков | 11 368 | 4 390 | 39% |
| REST API | 2 346 | 764 | 33% |
| API | 2 130 | 715 | 34% |
| Git | 1 953 | 666 | 34% |
| MS SQL | 1 183 | 489 | 41% |
| Микросервисная архитектура | 939 | 299 | 32% |
| ETL | 428 | 128 | 30% |
| DWH | 393 | 121 | 31% |
| DWH + ETL | 205 | 62 | 30% |
| ETL + REST API | 108 | 23 | 21% |
| DWH + ETL + REST API | 43 | 11 | 26% |
| DWH + Микросервисы | 32 | 7 | 22% |
| DWH + ETL + API + Git | 12 | **4** | — |

Практические пороги: **один редкий навык** оставляет сотни резюме, **два** — десятки,
**три и больше** — единицы. Перцентили осмысленны примерно от `n >= 50` с зарплатой,
то есть **не более двух узких навыков одновременно**.

## Фильтровать по редкому, классифицировать по частому

1. **Профроль** — каркас, даёт наибольшее сужение при нулевой потере смысла.
2. **Один–два самых редких навыка** из требований. По таблице выше DWH и ETL редкие,
   а Git и API почти шумовые — они есть у трети выборки и фильтруют слабо.
3. **Гео и опыт** — `area`, `relocation=living`, `experience`.
4. **Остальные требования не фильтровать, а измерять**: фасет `skill` покажет, у какой
   доли выборки есть Git, API, микросервисы. Это информативнее жёсткого отсева и не
   рушит выборку.

## Объединение синонимов вместо пересечения

Требование заказчика почти никогда не равно одному тегу. «Аналитик, работающий с
корпоративными хранилищами, витринами и ETL» — это семейство взаимозаменяемых навыков,
и правильная операция для них **ИЛИ, а не И**.

Сервер умеет только И, поэтому объединение делается запросами по отдельности и
склейкой по `hash`: один `harvest` на тег, затем `analyze.py tag1.json tag2.json ...`.

На том же каркасе (системный аналитик, Москва, `living`, опыт 6+):

| Навык | Всего |
|---|---|
| ETL | 428 |
| DWH | 393 |
| Big Data | 340 |
| Clickhouse | 292 |
| Airflow | 225 |
| Hadoop | 215 |
| Greenplum | 213 |
| OLAP | 84 |

| Способ | Резюме | Из них с зарплатой |
|---|---|---|
| Пересечение DWH+ETL+API+Git (И) | 12 | **4** |
| **Объединение восьми тегов (ИЛИ)** | **1 074** | **321** |

Разница в 80 раз по пригодным для статистики значениям. Пересечений между тегами 855 —
синонимы действительно перекрываются, но каждый добавляет своё.

И результат содержательно иной. По объединению: p25 = 250 000, **медиана 300 000**,
p75 = 400 000, p90 = 500 000. Для senior-подмножества (n = 69): медиана **350 000**.
Базовая роль без навыков давала медиану 250 000 — специализация на хранилищах
стоит примерно +20% к рынку роли. На пересечении из четырёх человек такой вывод
сделать было нельзя.

Оговорка: сбор ограничивался тремя страницами на тег, поэтому 1 074 — нижняя оценка
объединения.

**Расширение синонимами меняет смысл запроса и объявляется оператору до сбора** — см.
`protocol.md`.

## Как находить синонимы

Подсказки `api.hh.ru/suggests/skill_set` ищут по префиксу и пропускают почти всё:
«Хранилища данных», «Витрины данных», «Data Warehouse», «Data Mart», «Data Vault»,
«Data Engineering» дают **пустой ответ**. Полагаться на них при сборе синонимов нельзя.

Рабочий способ — **взять один заведомо верный seed-навык и прочитать фасет `skill`**:
он покажет топ-50 тегов, реально сочетающихся с ним в этой популяции, с частотами. Для
seed `DWH` (393 резюме) окружение выдало: ETL 269, ORACLE 167, Greenplum 150, Big Data
144, Power BI 135, Hadoop 130, Clickhouse 127, Apache Airflow 122, Oracle Pl/SQL 93,
Tableau 86, OLAP 59, СУБД 57.

Это словарь предметной области, построенный по данным, а не по догадкам. Порядок:
seed → фасет → отбор семантически близких → объединение по ИЛИ.

Отбирать в объединение нужно осмысленно: инструменты хранилищ (Greenplum, Clickhouse,
Hadoop, Airflow) — это та же функция, а BI-витрины (Power BI, Tableau) — уже соседняя,
их включение сместит выборку в сторону аналитиков отчётности. Границу семейства
определяет задача, и её надо фиксировать в отчёте.

## Грейд по названиям должностей

Фильтра по грейду нет, а текстом грейд отбирать нельзя: «ведущий» и «senior» стоят и в
названии резюме, и в прошлых должностях, а `pos` этих слоёв не различает. Зато `title`
и `shortExperience[].position` лежат **прямо в выдаче** — значит грейд определяется
после сбора (`analyze.py --classify grade`).

Пример (системный аналитик, Москва, опыт 6+, 400 резюме, 115 с зарплатой):

| Класс | Кол-во | n c ЗП | p25 | Медиана | p75 |
|---|---|---|---|---|---|
| Маркер в текущей должности | 88 | 22 | 230 000 | **270 000** | 350 000 |
| Маркер только в прошлых должностях | 215 | 71 | 180 000 | **250 000** | 300 000 |
| Без маркера | 93 | 18 | 150 000 | **180 000** | 250 000 |
| Junior-маркер | 4 | — | | | |

Градиент монотонный — классификация различает грейды, а не шумит. Заметный разрыв
медиан между «маркер сейчас» и «маркер только в прошлом» показывает, что различать
эти два случая имеет смысл.

**Немонотонный градиент — сигнал, что словарь маркеров шумит**, и его надо чинить, а
не публиковать.

Словарь маркеров: `senior`, `sr.`, `старш`, `ведущ`, `главн`, `lead`, `тимлид`,
`team lead`, `principal`. Проверять с якорем на границу слова.

Архитектор вынесен в **отдельный класс**: это скорее отдельная карьерная ветка, чем
грейд, и включение его в senior-маркеры завышает старший band. При первоначальной
разметке архитектор часто попадает в senior, и тогда приведенные выше цифры слегка
смещены вверх.

Тот же приём работает для отраслей, стека и любых смысловых признаков: собрать шире,
разметить у себя.

## Формат работы — пересекающиеся сегменты

Соискатель отмечает несколько форматов сразу. Например, при total порядка 11 000
фасет даёт ON_SITE ≈ 9 900 + REMOTE ≈ 10 900 + HYBRID ≈ 6 700 = 27 500 — сумма кратно
больше базы.

Доли не сложатся в 100%, «офисных» и «удалённых» нельзя противопоставлять. Корректная
формулировка — «готовы к удалёнке»; каждый сегмент считается отдельным запросом.

## Образование: факультет и год выпуска

Проверено вскрытием карточек выпускников одного вуза (порядка десятка записей об
образовании).

**В выдаче образования нет** — отобрать по нему сервер умеет (`pos=education`,
`filters.md`), а вернуть разобранные поля в списке нет. В карточке `/resume/<hash>`
поле `primaryEducation` (обёртка `{value: [...]}`) содержит по каждой записи:

| Поле | Смысл | Заполненность |
|---|---|---|
| `year` | **Год выпуска** | **надёжно** — заполнено практически всегда |
| `name` | Вуз | — |
| `organization` | **Факультет** | почти всегда |
| `result` | Специальность | почти всегда |
| `universityId` | ID вуза, сверяется с фильтром `university` | — |
| `facultyId`, `specialtyId` | Структурные ID | **ненадёжны** — заполнены у меньшинства |

Заполненность `year` проверена на небольшой выборке одного вуза; на широкой выборке
может быть ниже.

В замере диапазон годов охватывал несколько десятилетий и включал годы будущего —
планируемый выпуск у учащихся; при построении когорт их отсекать или выделять
отдельно.

**Факультет — свободный текст с разнобойным написанием.** В одной выборке встретились
«Юридический факультет, дневное отделение, бюджет», «юридический. Специальность
экологическое и земельное право», «Юридический». Точное совпадение не работает — нужна
нормализация: нижний регистр, отсечение хвоста после запятой или точки, сопоставление
по корню.

Справочников факультетов и специальностей в публичном API нет: `suggests/faculties`,
`suggests/specialties` → 404. Названия факультетов и специальностей брать с
**официального сайта учебного заведения**, а не выводить из собранных резюме и не
полагаться на память. Порядок: найти официальный сайт факультета → выписать перечень
программ → использовать как эталон для сопоставления с текстом резюме.

Даже с эталоном сопоставление остаётся нечётким: в резюме встретилось «Фундаментальная
математика и механика» против официального «Фундаментальные математика и механика».
Сравнивать по нормализованной форме и по корню, долю несопоставленных записей
указывать в отчёте.

### Стоимость подхода

Фильтр по вузу работает на сервере (`university=<id вуза>`, Москва, `living` —
десятки тысяч записей). **Факультет и специальность тоже отбираются сервером** —
текстом с `pos=education` и обязательным `exp_period` (`filters.md`): текст по
факультету отсекает подавляющее большинство вузовской выборки. Поштучно вскрывать
карточки ради факультета не нужно; из образования это требуется только для **года
выпуска**.

У текстового отбора своя цена: факультет в резюме написан вразнобой, поэтому одна
формулировка берёт не весь факультет. Семейство формулировок собирается несколькими
прогонами и склеивается по `hash` — как семейство навыков. Оценивать полноту следует
по доле, а не по абсолютному числу: если одна формулировка даёт заметно меньше
ожидаемой доли выпускников, разницу добирают синонимами (короткое имя, варианты
окончания).

Отсюда стратегия: сузить структурно (вуз, регион, период) и текстом по образованию,
и лишь затем вскрывать карточки — только если нужен год выпуска.

**Предстратификация до вскрытия.** Возрастные полосы сужают выборку на сервере и
делают вскрытие адресным: каждая полоса (например, 22–27, 28–33, 34–45) оставляет
десятки тысяч записей. Комбинируя вуз + возрастную полосу + профроль, можно
спускаться до сотен записей на когорту.

**Выборочный метод вместо сплошного.** Для медиан по когортам сплошной обход не нужен:
случайная выборка в 300–500 карточек на когорту даёт медиану с приемлемой точностью.
Это переводит задачу из «44 тысячи вскрытий» в «пара тысяч». Отбирать выборку
случайно по страницам (`randomPages`), а не первые N подряд — `order_by=relevance` не
случаен и первые страницы смещены.

**Часть задачи вообще не требует карточек.** Карьерный трек — компании, должности,
даты, нормализованная профессия и стаж в ней — целиком лежит в выдаче
(`shortExperience`, `professionExperience`). Карточки нужны исключительно ради
факультета и года выпуска.

`university` объединяется по **ИЛИ** (проверено: объединение двух крупных вузов
суммирует их пулы за вычетом небольшого пересечения — двойные дипломы). **Но
объединять вузы по своей инициативе нельзя** — см. `protocol.md`.

Пункт `education` присутствует в `settings.availableSettings` выдачи, но
URL-параметрами (`settings=education`, `search_settings=education`) не включается —
настройка хранится на аккаунте. Если включить показ образования в интерфейсе поиска
(кнопка «Вид»), образование может появиться прямо в выдаче и снять необходимость
вскрывать карточки. **Не проверено** — требует изменения настроек аккаунта.

## Когорты «лет после выпуска»

При доступном годе выпуска когорты строятся точно: `текущий год − year`.

Резерв, когда карточки вскрывать нельзя, — `totalExperience` (стаж в месяцах, есть у
100% записей выдачи); он ближе к смыслу «лет после выпуска», чем возраст (`age`
заполнен у ~90%). Когорты 0–2 / 3–7 / 8–15 / 16+ лет стажа строятся без вскрытия.

Отличие честно назвать: стаж не равен времени с выпуска, часть людей начинала работать
до диплома или делала перерывы.

## Знаменатель у разрезов по вскрытым карточкам

Карточки вскрываются не у всей выборки: суточная квота и время оператора обычно
оставляют 15–25%. Измерение, живущее только в карточке — факультет, специальность,
год выпуска, — описывает эту подвыборку, а не пул под фильтром.

Правило публикации: **две доли в каждой строке** — от всей выборки и от вскрытой
части, — и «карточка не вскрыта» отдельной строкой таблицы, а не выброшенными
записями. Так, доля признака во вскрытой части может в несколько раз превышать долю
от всей выборки; одна доля без второй читается как утверждение о пуле и завышает
или занижает его кратно.

Категорию «карточка не вскрыта» держать в тех же таблицах и при подсчёте медиан: у неё
есть собственные зарплатные значения из выдачи, и её отличие от вскрытой части — это
проверка на смещение отбора карточек. Совпадение медиан означает, что вскрывали
случайно; расхождение — что нет, и об этом нужно сказать в отчёте.

## Один спек по нескольким сущностям

Повторяющаяся форма задачи: тот же спек прогоняется по N сущностям (пять вузов, три
города, четыре профроли), а ответом служит сравнительная матрица. Порядок работы:

- один и тот же набор параметров на все сущности, различие ровно в одном id; любое
  другое расхождение делает столбцы несопоставимыми;
- прогон на сущность сохраняется отдельным файлом (`tag` в `harvest`), слияние — уже
  в `analyze.py`, а не в браузере;
- размеры пулов различаются на порядок, поэтому сравниваются доли внутри сущности, и
  порог n применяется к каждой ячейке отдельно, а не к матрице целиком;
- **перед сравнением одной категории между сущностями проверить, что метка означает у
  каждой одно и то же.** В одном замере категория «Руководитель и управление» у
  технического вуза собрала линейный производственный менеджмент (мастер, начальник
  участка), у классического университета — корпоративное управление; доли формально
  считаются, а сравнивать их нельзя. Проверка — прочитать
  по десятку попавших в категорию заголовков на каждую сущность; при расхождении либо
  дробить категорию, либо выносить оговорку в отчёт.
